# CacheStorm vs Redis differential compatibility report

Generated by the harness in `tests/compat/` (build tag `compat`). Every case starts with `FLUSHALL` on both servers and runs the same command sequence against real Redis (`redis:7.4-alpine`, `--save '' --appendonly no`, random port) and a freshly built CacheStorm (HTTP, persistence and metrics off, random ports). The harness compares every reply byte for byte as raw RESP2. It then compares the resulting keyspace (db 0, and db 1 for SELECT-related cases): TYPE, full contents, and whether a TTL is set.

The only normalizations are: TTL/PTTL within ±1 s / ±1.5 s, `[sorted]` for set-like replies whose order Redis leaves unspecified, `[full scan, sorted]` for SCAN-family iteration (the cursor loop runs until 0, then results are deduplicated and sorted; HSCAN/ZSCAN pairs are not deduplicated), `[type only]` / `[length only]` for random members and auto-generated stream IDs. Each step's normalization is shown next to it.

CacheStorm was built from main on 2026-10-25.

## Rerun

```bash
# full run (needs docker; builds CacheStorm from the repo root; ~35 s)
go test -tags compat -count=1 -v -timeout 15m ./tests/compat/

# write the generated failure report somewhere (default: $TMPDIR/cachestorm-compat-results.md)
COMPAT_OUT=/tmp/compat.md go test -tags compat -count=1 -timeout 15m ./tests/compat/

# a subset: by subtest path or by substring of "group/name"
go test -tags compat -count=1 -v ./tests/compat/ -run 'TestCompat/pubsub'
COMPAT_FILTER=lists/pop-count go test -tags compat -count=1 -v ./tests/compat/

# against servers that are already running / a prebuilt binary / another image
COMPAT_REDIS_ADDR=127.0.0.1:6379 COMPAT_CACHESTORM_ADDR=127.0.0.1:6380 go test -tags compat -count=1 ./tests/compat/
COMPAT_CACHESTORM_BIN=./cachestorm COMPAT_REDIS_IMAGE=redis:7.2-alpine go test -tags compat -count=1 ./tests/compat/
```

Without `-tags compat`, `go test ./...` sees only the untagged `doc.go` and reports `[no test files]`. If docker is unavailable and `COMPAT_REDIS_ADDR` is unset, the test skips. The Redis container is started with `--rm` and removed with `docker rm -f` in `t.Cleanup`.

To refresh this file, write the generated body with `COMPAT_OUT` and paste it below this header. Severity and classification for each case live in `tests/compat/verdicts_test.go`. A failure with no entry there appears under "Unclassified".

## Summary

| Run | Cases | Match Redis | Differ |
|---|---|---|---|
| 2026-10-23, first run of the harness | 307 | 138 | 169 (27 severity 1) |
| 2026-10-25 | 340 | 337 | 3 (none severity 1 or 2) |

The 33 cases added since the first run cover stream trimming, consumer groups, claims and XINFO.

The three remaining differences:

1. `strings/set-exat-pxat-past` and `keys/expiretime`: an expiry instant after the year 2262 is capped, because the store keeps expiry times as int64 nanoseconds, so TTL and EXPIRETIME report the capped instant instead of Redis' value. Storing expiry in milliseconds would remove the cap.
2. `lua/redis-call-errors`: a script that fails to compile carries gopher-lua's parser message (`near 'error': parse error`) where Lua 5.1 says `'=' expected near 'error'`. This is a property of the Lua implementation and is classified as intentional.

CI runs the harness in ratchet mode (`COMPAT_RATCHET=1`): a difference listed in `verdicts_test.go` is logged, and a new difference, or a listed one that now matches Redis, fails the job.

## Severity 3: edge cases and error-text differences

### strings/set-exat-pxat-past

**bug**: expiry instants after the year 2262 are capped (expiry is stored as int64 nanoseconds), so TTL reports the capped instant

```
   c0> SET k v PXAT 1
     both:   "+OK\r\n"
   c0> GET k
     both:   "$-1\r\n"
   c0> SET k2 v EXAT 1
     both:   "+OK\r\n"
   c0> EXISTS k2
     both:   ":0\r\n"
   c0> SET k3 v EXAT 99999999999
     both:   "+OK\r\n"
!! c0> TTL k3
     redis:  ":98207114305\r\n"
     cstorm: ":7430399943\r\n"
```

### keys/expiretime

**bug**: expiry instants after the year 2262 are capped (expiry is stored as int64 nanoseconds), so EXPIRETIME/PEXPIRETIME/TTL report the capped instant

```
   c0> SET k v
     both:   "+OK\r\n"
   c0> EXPIREAT k 33177117420
     both:   ":1\r\n"
!! c0> EXPIRETIME k
     redis:  ":33177117420\r\n"
     cstorm: ":9223285636\r\n"
!! c0> PEXPIRETIME k
     redis:  ":33177117420000\r\n"
     cstorm: ":9223285636854\r\n"
   c0> PEXPIREAT k 33177117420000
     both:   ":1\r\n"
!! c0> TTL k
     redis:  ":31384231726\r\n"
     cstorm: ":7430399943\r\n"
```

### lua/redis-call-errors

**intentional difference**: compile errors carry gopher-lua's parser message ("near 'error': parse error") instead of Lua 5.1's

```
   c0> SET s v
     both:   "+OK\r\n"
   c0> EVAL "return redis.call('INCR',KEYS[1])" 1 s
     both:   "-ERR value is not an integer or out of range script: da8455f0535fd532821b3713a4eccd80fc4b8457, on @user_script:1.\r\n"
   c0> EVAL "return redis.pcall('INCR',KEYS[1])" 1 s
     both:   "-ERR value is not an integer or out of range\r\n"
   c0> EVAL "local r = redis.pcall('INCR',KEYS[1]) return type(r)" 1 s
     both:   "$5\r\ntable\r\n"
   c0> EVAL "return redis.call('NOSUCHCMD')" 0
     both:   "-ERR Unknown Redis command called from script script: ee4002f488cb0514b4fbe5979e61c3bf43204edb, on @user_script:1.\r\n"
!! c0> EVAL "syntax error here" 0
     redis:  "-ERR Error compiling script (new function): user_script:1: '=' expected near 'error'\r\n"
     cstorm: "-ERR Error compiling script (new function): user_script:1: near 'error': parse error\r\n"
   c0> EVAL error('custom') 0
     both:   "-ERR user_script:1: custom script: 999b995fd1d2b0eab82a608b66e4c8b1c62f3265, on @user_script:1.\r\n"
```
