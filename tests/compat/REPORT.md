# CacheStorm vs Redis differential compatibility report

Generated by the harness in `tests/compat/` (build tag `compat`). Every case starts with `FLUSHALL` on both servers and runs the same command sequence against real Redis (`redis:7.4-alpine`, `--save '' --appendonly no`, random port) and a freshly built CacheStorm (HTTP, persistence and metrics off, random ports). The harness compares every reply byte for byte as raw RESP2. It then compares the resulting keyspace (db 0, and db 1 for SELECT-related cases): TYPE, full contents, and whether a TTL is set.

The only normalizations are: TTL/PTTL within ±1 s / ±1.5 s, `[sorted]` for set-like replies whose order Redis leaves unspecified, `[full scan, sorted]` for SCAN-family iteration (the cursor loop runs until 0, then results are deduplicated and sorted; HSCAN/ZSCAN pairs are not deduplicated), `[type only]` / `[length only]` for random members and auto-generated stream IDs. Each step's normalization is shown next to it.

CacheStorm was built from the working tree at commit 58d78e2 plus the uncommitted changes present on 2026-10-23. Other people were editing `internal/` while this ran.

Without `-tags compat`, `go test ./...` sees only the untagged `doc.go` and reports `[no test files]`. If docker is unavailable and `COMPAT_REDIS_ADDR` is unset, the test skips. The Redis container is started with `--rm` and removed with `docker rm -f` in `t.Cleanup`.

## Top failures by impact

1. **SELECT is a no-op: all 16 databases share one keyspace** (`db/*`, `transactions/multi-select`, `lua/lua-select-isolated`, `transactions/watch-other-db-no-abort`). `FLUSHDB` in db 1 wipes db 0. `MOVE` replies 1 and does nothing. `SWAPDB` does nothing. Two connections on different DBs overwrite each other's keys. `SELECT 16` is accepted. This is data loss for any app that uses more than one DB number.
2. **Pub/Sub never delivers messages** (all 10 delivery cases: SUBSCRIBE, PSUBSCRIBE, SSUBSCRIBE, binary payload, PUBLISH from MULTI). `PUBLISH` returns the correct receiver count (`:1`), but no `message`/`pmessage`/`smessage` frame reaches the subscriber socket within 2 s. The suspicion is confirmed. The subscribe acks are also malformed: `+subscribe` is a simple string where Redis sends a bulk string, `SUBSCRIBE a b` reports count 2 on the first ack, and `UNSUBSCRIBE` with no args returns a nil channel.
3. **Command names are case-sensitive** (`misc/case-insensitive`). `set a 1` and `GeT a` return `ERR unknown command`. `Router.Get` looks up `r.commands[name]` without upper-casing, and HEAD has the same code. Clients that send lowercase names (go-redis, ioredis and others) cannot run a single command.
4. **Lua scripts get no `KEYS`/`ARGV` tables** (`lua/*`). `KEYS[1]` raises "attempt to index a non-table object(nil)", so almost every real script fails. Several commands, including XADD, PING, PUBLISH and INCRBYFLOAT, are "unknown command ... called from Lua script". `redis.call` errors come back as bulk strings instead of raising, so a script keeps going after a failed write. `cjson` is missing. Return conversion is wrong: `{ok=..}`/`{err=..}` become arrays, `false` becomes `:0`, and floats are not truncated.
5. **A transaction with a wrong-arity command runs partially** (`transactions/execabort-wrong-arity`). `GET` with no args inside MULTI is `QUEUED`, and EXEC applies the other commands. Redis replies `EXECABORT` and applies nothing.
6. **SSCAN/HSCAN iteration loses data** (`sets/sscan`, `hashes/hscan`). A full cursor loop over a 40-member set returned only 27 members. HSCAN over 50 fields returned duplicates and skipped fields. Clients that use SCAN to export, migrate or clean up data silently miss elements.
7. **LPOP/RPOP `<count>` ignores the count** (`lists/pop-count`). It pops one element and replies with a bulk string where an array is expected. ZRANDMEMBER `<count>` has the same problem.
8. **XREADGROUP reply shape is wrong** (`streams/xreadgroup-ack-pending`, `streams/xpending-extended-shape`). Entries come back flattened as `id, fields, id, fields` instead of `[[id, fields], ...]`, which breaks every stream consumer client. XPENDING consumer counts are integers instead of bulk strings, consumers with everything acked are still listed, and reading history with ID `0` returns nil.
9. **Sorted-set range queries**: `ZRANGE ... BYSCORE REV` and `ZRANGE ... BYLEX REV` return empty. Exclusive bounds such as `(3` are rejected by ZCOUNT, ZREVRANGEBYSCORE, ZREMRANGEBYSCORE and ZRANGESTORE. `-inf`/`+inf` scores are rejected by ZADD. ZPOPMAX with a count returns ascending order. ZMPOP replies are flat instead of nested.
10. **Other common-path problems**:
    - Aborted `EXEC` (WATCH conflict) replies `$-1` where Redis sends `*-1`, and `EXPIRE` on a watched key does not abort.
    - `SET k v NX GET` returns an error.
    - `SET` accepts `EX`+`PX` together.
    - `PERSIST` returns 1 on a key with no TTL.
    - `PEXPIRE k 0` errors and leaves the key alive.
    - Glob character classes (`[1-3]`) never match in KEYS or ZSCAN MATCH.
    - `SCAN ... TYPE` is unsupported.
    - Inline commands (`echo PING | nc`) drop the connection.
    - HELLO is missing.
    - Keys containing NUL/CR/LF are rejected.
    - `INCRBYFLOAT 0.1` then `0.2` gives `0.30000000000000004`.

The blocking commands (BLPOP, BRPOP, BLMOVE, BRPOPLPUSH, BLMPOP, BZPOPMIN, BZMPOP, XREAD BLOCK) all wake up correctly with timeout 0 when a second connection pushes after 200 ms, honor fractional timeouts, and serve two waiters in FIFO order. No case hung. BLMOVE/BRPOPLPUSH timeouts reply `$-1` where Redis sends `*-1`.

About 100 of the severity-3 failures are error-text-only. They mostly come from one root cause: arity errors say `ERR wrong number of arguments` without `for '<cmd>' command`, and unknown commands omit `with args beginning with:`. Other error-text failures are `-key not found` with no `ERR` prefix, where Redis says `-ERR no such key`, and generic `ERR invalid argument` / `ERR syntax error` in place of Redis' specific messages.

Flaky: `blocking/blpop-wrongtype` failed in 2 of 3 runs on the CacheStorm side, returning nil after the timeout instead of WRONGTYPE. The Redis side and every other case were stable across 3 runs.
